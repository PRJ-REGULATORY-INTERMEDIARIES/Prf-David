## 1. Re-execution performed
**Script:** `00_ADMIN/scripts/r04_r3_r4_audit.py`. It is an independent **Python re-implementation** of the R4.2C-R pattern rule (copied from the logic of `build_r4_2cr_true_terra_review.ps1`, `Pattern-Row`) and of the R4.2D tallies. It reads the frozen inputs and writes only to `04_R3_R4/R4_RECOMPUTATION_RESULTS.csv`.

The original PowerShell scripts were **not** re-run. Their root-path convention writes into `R4_CROSS_DOMAIN_VALIDATION/` (see the planning exploration), and running them would have required copying the whole repository. The re-implementation achieves the same check — recomputing every number from the inputs — without that risk.

## 3. New or sharpened findings (not stated explicitly in the R4 documents)

1. **COUNTERPART = RECIPIENT holds in 1,404/1,404 rows** (409 of them are both empty). It is a deterministic consequence of `Recipient=$counterpart` in the extraction script. The R4 work note acknowledges that the extractor "copied one span", and it identifies ACTION_OBJECT = INFORMATION_OBJECT as "one variable currently coded twice". It does not say that *all* R4.2 field values come from regular-expression matching. Meanwhile, `EXTRACTION_MODEL` names a model runtime on every row. **Recommended wording for future reports:** "structural fields generated by a regex-based script authored and executed in a Codex/GPT-5 session". This is classified as `PROVENANCE_CLARIFICATION`, not as a defect in the human diagnostic: the human review correctly identified the symptoms.
2. **No R4.2 rows for DSA Art 37** (independent audit). The R4 extraction therefore offers no historical relational baseline for one of the case articles selected in R07.
3. **What the defect taxonomy does and does not cover.** Every defect class concerns the *structural extraction of propositions* (actor, verb, modality, object, counterpart, recipient). None concerns *intermediary identification*, *function/mechanism classification* or Rotem's variables. The taxonomy therefore supports the comparison only indirectly, as a catalogue of risks for any provision-level child layer (see `10_SENSITIVITY/ADVERSARIAL_CASES.md`).
